# Downloader compatibility

## Boundary

Yoink runs one Telegram bot with optional functional modules. Personal cookies belong to a user, not to a module. The global cookie pool is a separate credential source and requires enabled, authorized use. Runtime bot identifiers bind Telegram routing and receipts to the configured account, not to separate module bots.

The Rust Telegram adapter remains experimental and opt-in. Private commands are owner-only. A separate `YOINK_RUST_TELEGRAM_GROUPS_ENABLED=true` setting enables media commands for known, authorized users in registered groups and topics. Production Python services and PostgreSQL data are unchanged. Engine support, a Telegram command, and verified end-to-end behavior are separate milestones.

The existing [media fixture](../../backend/scripts/test-media.mjs) already exercises real container processing, native video delivery, crash/retry/cancellation handling, file-ID cache reuse and recovery, versioned cookies/proxies, revocation and credential redaction. A bounded private settings editor covers supported format and subtitle preferences. `/lang` selects the saved interface language. Bare `/subs` edits standalone-subtitle language and automatic-subtitle preferences. Other legacy settings workflows remain unported.

## Command contract

- `/download URL` retains its single-video grammar and does not accept flags. It now inherits saved video settings at admission.
- `/video URL`, `/audio URL` and `/image URL` select video, audio and gallery-image modes.
- `/subs URL` sends standalone SRT/VTT documents, falling back to ASS/SSA, without downloading video. It accepts only `--subtitle-language CODE` and `--subtitle-auto true|false`. Bare `/subs` opens a private menu for standalone-subtitle language and automatic-subtitle preferences. This command does not embed or burn subtitles into video.
- `/playlist URL` requests entries 1 through 20. `/playlist N URL` requests 1 through N. `/audio N URL` and `/video N URL` request only entry N. Explicit `A-B` preserves order, and `-N` selects the final N entries. A range before the URL is always a playlist selector, even when the URL has a `t`/`start` query parameter. Domain/protocol ranges are bounded to 100 entries, while configured worker item/byte budgets may be tighter.
- `/cut URL START END` remains an immediate request. `/cut URL` and `/cut URL START` instead open the private interactive clip dialog. Unsigned decimal seconds and colon-form times are accepted. A numeric END smaller than START is a duration, otherwise it is absolute. A colon-form END is always absolute. For `/video` and `/audio`, trailing `URL START DURATION` or `URL?t=START DURATION` arguments instead use numeric durations. Parser tests and EN/RU help distinguish these forms.
- Unknown or malformed arguments must not create operations. Source URLs and credential-bearing query values stay out of debug output and error replies.

## Plain URL messages

A visible Telegram `url` entity submits a video through the same authorization, saved preferences, progress, cache and message-based idempotency path as `/video`. Text before the URL may contain Unicode, including emoji. Entity ranges use UTF-16 code units and must land on character boundaries. The adapter never interprets a hidden `text_link` target as a download. It ignores captions, missing URL entities, command messages and content inserted via another bot. Multiple URL entities, malformed ranges, credentials in URLs and unsupported trailing arguments produce fixed localized guidance without admission or source echo.

A trailing `START DURATION` or `START END_TIME` clips the video. Numeric durations are added to the start, while colon times are absolute. A single trailing time requires a unique valid `t` or `start` query marker. Two explicit times override a valid URL timestamp. A timestamp without trailing times opens the durable private end-time dialog, which requires summary confirmation and follows the interactive end-value rules below. Groups must supply a complete clip or use an explicit command. Active `/cut` input keeps precedence over plain URL handling. Use `/cancel` before starting an unrelated implicit download during a clip dialog.

Private messages remain owner-only. In opted-in groups, a plain URL must reply to this bot or originate through this bot's inline mode, and normal user/group/topic authorization still applies. Ordinary group links are silent. Replies, uploads and cached sends stay in the incoming chat/topic with the original message reference. This routing accepts an existing inline-origin message, but does not implement inline search itself.

Music-provider domains used by the legacy Music plugin are reserved for that module, including their subdomains. They do not trigger implicit video downloads. Gallery selection still needs `/image`, and saved quality `ask` still requires an explicit concrete format instead of an interactive picker. Unlike the legacy thirty-second age cutoff, message age does not discard durable replay. Hidden-link extraction, automatic registration, music resolution, automatic message deletion and private redirection are not part of this path.

## Subtitle preferences

Owner-private bare `/subs` opens a dedicated menu for standalone subtitle documents. Language choices include the legacy EN/RU/ZH/JA/AR/HI/DE/FR/ES/PT presets and `zh-Hans`. Custom valid tags saved through `/settings subs_lang CODE` remain visible. The automatic-subtitle setting controls whether extraction may use automatic tracks. The menu does not claim tracks exist for a particular source and performs no extraction or media admission.

Buttons change only `subs_lang` or `subs_auto` and the shared settings revision. Authorization and bans are rechecked, and callbacks require an accessible message from this bot in the owner's private chat. Stale, replayed, malformed and old unversioned callbacks cannot mutate preferences. Changes through `/settings` or `/proxy` can invalidate `/subs` buttons, and subtitle choices can invalidate their buttons. Reopen `/subs` to recover from stale buttons or an unacknowledged Telegram edit.

The menu uses the saved interface language independently of the selected subtitle language. `/subs URL` continues to inherit these preferences unless explicit subtitle flags override them. Existing admitted jobs keep their frozen subtitle options. No enable/disable control for embedding is exposed, and `subs_enabled` remains unchanged. Standalone subtitle requests still work when that legacy embedding preference is disabled. Group download permissions are unchanged, but groups cannot use this settings menu. No schema migration is required.

`just test-media subtitle-settings` runs the dedicated acceptance scenario against rebuilt images.

## Interface language

Owner-private `/lang` opens English and Russian choices. It changes the existing user's `language` and `updated_at` fields only, without creating a user or altering roles, grants, downloader preferences, cookies, jobs or cached media. Callbacks require an accessible message from this bot in the owner's private chat. Ban and configured-owner checks run again in the write transaction. Each accepted choice, including the current language, advances a monotonic revision. Older buttons cannot overwrite a later choice, including after restart or a switch back to the original language.

New command replies and callback responses prefer a supported saved `users.language` over Telegram's `language_code`. Missing or unsupported saved values fall back to Telegram metadata, then English. A failed locale lookup also falls back without exposing database errors or changing access decisions. Successful selection updates the menu text in the new language and removes its keyboard. Already-created progress messages retain their stored language, while new admissions use the current choice. Groups cannot change the preference through `/lang`, and existing group authorization is unchanged.

`just test-media language` runs the focused Bot API acceptance scenario. No schema migration or production configuration change is required.

## Interactive clips

Owner-private `/cut URL` asks for the start time, then the end time. `/cut URL START` skips the first question. Unsigned decimal seconds and colon times use the same parser as inline clips. In the interactive end prompt, a numeric value less than or equal to the start is a duration. A colon time is always absolute and must exceed the start. The immediate inline form retains its existing strictly-less-than duration rule. Interactive forms do not accept format flags and use saved preferences at confirmation.

The summary offers confirm, edit times and cancel. Bare `/cancel`, `cancel` and `отмена` cancel a pending draft. `/cancel UUID` still cancels a media operation. Bare `/cut` resumes the persisted state, including after a lost prompt or process restart. Other commands are not interpreted as time input. Unlike legacy `/cut URL`, this opens only the clip dialog, not the general format picker. Conversation messages are retained rather than deleted. Prompts and errors do not echo source URLs.

Migration v6 stores one draft per actor, bot and private chat. Repeated or older message IDs cannot advance a newer draft. Session IDs and revisions reject old buttons after edits, cancellation or replacement. Cancellation retains a tombstone so replay cannot resurrect the draft. Drafts have no automatic expiry and stay until cancellation or replacement. Older binaries reject the v6 schema, so rollback requires a compatible binary or restoration of a pre-migration backup. Every service action rechecks current identity authorization, and callbacks additionally require an accessible message from this bot in the owner's private chat.

Confirmation first persists an immutable `Confirming` state. From then on, edit, cancel and replacement cannot discard an admission whose outcome is uncertain. The normal preferred-settings admission path uses a stable session key rather than the callback delivery ID. A retry after a crash between admission and recording its result finds the original operation and frozen settings. Failed admission leaves a retryable confirmation. Correct invalid saved preferences through `/settings`, then confirm again. Once admitted, use `/job UUID` or `/cancel UUID` for the operation. Repeated confirmation cannot restart delivery.

## Clearing your cache

Owner-private `/uncache URL` removes cached file-ID batches for the exact canonical source URL, across media modes, clip ranges, formats and credential versions, only within the sender's actor/current-bot partition. URL parsing follows the stored request representation. Query strings and fragments remain part of the match. The command rejects missing/extra arguments, non-HTTP(S) URLs, embedded credentials and oversized input. It does not require valid saved format preferences, echo the URL, create a download, or delete Telegram files.

Other actors and bots, other URLs, imported legacy cache, credentials, settings, operation history and delivery receipts remain unchanged. This actor-only behavior was selected explicitly instead of copying legacy `/uncache`'s shared administrative scope. `/reload_cache` is not exposed, because the legacy handler only acknowledges a reload without performing one.

Clear and a per-actor/bot message watermark commit in one transaction. Repeated or older command messages do not delete entries that have since been recreated, even after restart or when the replay changes the URL. A fresh message can clear again. Ban and role checks apply before and at the mutation boundary. Groups and non-owner private senders cannot invoke the command. Migration v7 adds the durable watermark, so rollback needs a v7-compatible binary or a pre-migration backup.

Clearing affects subsequent cache lookups, not active work. A job may already hold a cached batch, and a running download may publish a new entry after the clear. The command neither cancels those jobs nor changes the replay of a completed operation. Downloading the URL again with a new message after a clear uploads fresh output when no active job has repopulated the cache.

## Personal cookie controls

Owner-private `/cookie` lists personal records marked valid in pages of ten, reading only metadata. `/cookie DOMAIN` returns a record count or a missing/invalid status, never cookie values. Domains use strict bare-hostname syntax, case-insensitive with surrounding dots removed. A bare domain only inspects status, without fetching it or expanding provider aliases or subdomain wildcards. Malformed imported domains render as a fixed invalid-entry label, without echoing their text. Status reads cap content at 512 KiB and recognize Netscape HttpOnly records. Invalidated, malformed, oversized or canonically ambiguous imported records are reported as invalid rather than missing or a partial count.

`/cookie del DOMAIN` removes matching personal records. `/cookie clear` removes all of the sender's personal records, including invalid ones. Both preserve other users' cookies and every global-pool record, including pool records owned by the sender. They do not change preferences, jobs, delivery receipts or cache rows. Invalid saved format preferences do not block cookie controls. Groups and non-owner private senders remain outside this experimental command boundary.

Deletion and a per-user Telegram message watermark commit in one transaction, with fresh authorization at the mutation boundary. A repeated or older command cannot remove cookies stored since the original command, even after restart or when the replay changes its arguments. A deletion that matches nothing still advances the watermark. Migration v8 adds this ledger. Rollback requires a compatible binary or a pre-migration backup.

A document captioned `/cookie DOMAIN` replaces that domain's personal cookie file. Bare `/cookie` on a document derives the domain from the filename stem, for example `youtube.com.txt`. Explicit domains take precedence. Foreign-bot commands, unrelated captions and group documents are ignored. Domain parsing stays strict, and document captions never enter the media or clip command parser.

The adapter checks authorization and the mutation watermark before calling Telegram `getFile`. For cloud Bot API it fetches only a validated relative path from the configured origin and refuses redirects. Local Bot API absolute paths require the explicit root mapping described below. Both paths enforce a 512 KiB file limit without creating temporary files. Attachment metadata, `getFile` size, response length and actual streamed bytes are checked independently. Files must contain strict UTF-8 Netscape text with at least one valid record. File contents, names, IDs and download URLs never appear in replies or logs. `YOINK_RUST_TELEGRAM_COOKIE_UPLOAD_TIMEOUT_SECS` bounds the complete `getFile` and body download, defaulting to 30 seconds. A failed fetch or invalid file leaves stored cookies and the watermark unchanged.

The existing Compose deployment uses TDLight local mode. Enable local document reads by setting `YOINK_RUST_BOT_API_FILE_ROOT` to the remote directory prefix, `YOINK_RUST_TELEGRAM_LOCAL_FILE_ROOT` to its read-only mount inside the Rust container, and `YOINK_RUST_BOT_API_URL` to the local API origin. Prefer mounting only this bot's document directory. Neither root may be `/` or contain traversal components. Absolute paths outside the configured prefix, symlinks at any traversed component and non-regular files are rejected. Reads use directory file descriptors and `openat` with `NOFOLLOW`, not a check-then-open pathname. Blocking filesystem work runs in a dedicated thread, with one shared read slot per adapter configuration. Cancellation retains that slot until the underlying read exits, so repeated timeouts cannot accumulate blocking workers. The response deadline cannot interrupt kernel filesystem I/O. Use a local disk mount, not a network or FUSE filesystem. A stuck mount may require operator recovery. Its outstanding read does not hold up Tokio runtime shutdown. This feature does not add or change a production mount. Without the paired configuration, absolute file paths are rejected.

Successful replacement rechecks authorization and advances the same per-user watermark as deletion in an Immediate transaction. It removes matching canonical-domain personal aliases and inserts one valid record with a fresh ID. Even reuploading identical bytes invalidates the old reference. Old uploads cannot overwrite a newer replacement or resurrect cookies after deletion, including after restart. Other personal domains and the global pool remain unchanged. A failed acknowledgement does not undo a committed replacement. Check `/cookie DOMAIN` or resend with a fresh message if the result is uncertain.

Removing or replacing a selected cookie invalidates its frozen reference. Queued execution and delivery rechecks fail rather than switching an existing job to another personal cookie or the global pool. An already running worker may finish its network requests. A new admission can select a permitted pool cookie through the existing resolver. Browser tokens, web management and pool administration are not implemented by these commands. The native `just test-media cookie-uploads` scenario exercises document ingestion separately from `just test-media cookies`, which covers listing and deletion.

## Personal cookie URL import

Owner-private `/cookie URL [DOMAIN]` fetches an HTTP(S) Netscape cookie file. An explicit domain uses the same strict canonicalization as document uploads. Without it, the domain comes from the original URL's host using the legacy `www.` and provider-alias normalization. Redirect hosts and file names do not choose the storage domain. Source URLs cannot contain credentials, fragments, whitespace or control characters. Arguments and source lengths are bounded, and URLs, query tokens and file contents stay out of replies and diagnostics.

The adapter checks authorization and the shared cookie mutation watermark before fetching. It uses a separate direct client without ambient proxies, saved credentials, cookies or a Referer header. All resolved addresses must be public and are pinned for the connection. Each of at most five redirects goes through the same validation, and HTTPS-to-HTTP redirects are rejected. No browser execution, archive extraction, custom request headers or authentication forwarding is supported.

Responses are limited to 512 KiB of strict UTF-8. Oversized declared lengths or streamed bodies, invalid Netscape text, unsupported response encodings and failed HTTP requests leave cookies and the watermark unchanged. `YOINK_RUST_COOKIE_IMPORT_TIMEOUT_SECS` covers concurrency wait, DNS, redirects and the complete body. The HTTP fetch and blocking DNS resolver each have four shared slots. A timed-out DNS caller does not release its resolver slot until the underlying lookup returns, and stuck resolver threads do not block runtime shutdown. Cookie persistence happens outside the transport deadline so the deadline cannot interrupt a commit. Successful imports use the existing personal-cookie replacement transaction, including fresh authorization, a new row ID and the common watermark shared with document upload, delete and clear. A delayed response cannot overwrite a newer cookie mutation. Replaying an old import after restart cannot refetch or resurrect a removed cookie.

Public-address checks are the default. `YOINK_RUST_COOKIE_IMPORT_PRIVATE_ORIGINS` explicitly permits exact literal-IP origins when an operator needs a trusted internal source. It has no effect on other origins, ports, DNS hostnames or the media worker's policy. The native fixture opts in only to its isolated local HTTP origin. This exception can expose paths on that endpoint to the owner, so leave it empty for production unless needed. HTTP source URLs transfer the cookie file in plaintext. Prefer HTTPS or document upload.

`just test-media cookie-urls` exercises the native Bot API adapter with actual HTTP responses and cookie-authenticated media delivery. It checks the 512 KiB boundary, invalid bodies/encodings, private redirects and loops, authorization changes during fetch, a newer mutation overtaking a delayed response, and document/delete/clear replay across restart. The fixture restores cookies, user fields, settings and mutation watermarks. Rust regressions cover public/special/mixed DNS answers, redirect parsing and downgrade rejection, exact origin exceptions, and resolver capacity after caller cancellation. External providers and DNS rebinding against live infrastructure are not exercised. No schema migration is added, and global-pool records remain separate.

## Proxy usage

Owner-private `/proxy` shows whether proxy use is enabled and offers an explicit enable or disable button. It accepts no arguments and does not expose, accept or replace proxy credentials. A valid personal proxy takes precedence over the configured system proxy. Either can enable the menu, unlike the legacy system-only guard. Worker origin restrictions still apply. Missing or malformed configuration cannot be enabled. Disabling remains available when configuration or unrelated saved format preferences are corrupt.

Buttons require the owner's private chat and an accessible message from the current bot. Every action checks current authorization, and mutation rechecks bans and the saved settings revision. An old button cannot undo a newer choice, including after restart. Proxy changes share the `updated_at` revision with the settings editor, so edits in either menu can make the other's buttons stale. Reopen `/proxy` to read current state after a rejected button or failed Telegram edit. No schema migration or media operation is created. The generic `/settings` editor does not expose proxy toggles.

A toggle affects subsequent admissions, not the frozen route of an existing operation. Execution and delivery reject a frozen direct route when proxy use becomes enabled, and reject a frozen proxy route when it becomes disabled. They do not silently reroute or deliver results under a different network policy. A worker already running may finish its network requests, but the delivery recheck prevents sending invalidated results. Resubmit the download with a new message under the intended policy.

## Saved settings and overrides

Owner-private `/settings` and `/format` open the same EN/RU editor for `quality`, `codec`, `container`, `audio_codec`, `send_as_file`, `gallery_zip`, `subs_lang` and `subs_auto`. `/settings FIELD VALUE` and `/format FIELD VALUE` also accept explicit values. Values are closed choices shown by the buttons, except subtitle language, which accepts a valid exact tag up to the imported column's eight-character limit. Unknown fields, raw arguments, proxy URLs, credentials, interactive `ask` and embedding are not writable through this editor. It deliberately replaces the legacy `/settings` buttons that merely suggested other commands, rather than advertising unavailable features.

Buttons require an accessible message from this bot in the owner's private chat. Each mutation rechecks identity and global bans. The SQL upsert changes only the selected field and its timestamp, and creates default preferences only for an existing authorized user. Mutation buttons carry the settings `updated_at` revision. Writes compare it atomically and advance it monotonically. A stale button or replay after another choice cannot overwrite that choice and tells the user to reopen `/settings`. Text commands set absolute values without a revision precondition. No new schema or media operation is needed. A failed Telegram reply/edit does not undo a committed setting. Reopening `/settings` reads the current persisted values. Groups, non-owner private users, user registration and other legacy configuration workflows remain outside this editor.

Saved video settings apply quality, video codec, container and file delivery. Audio mode applies audio codec and file delivery, ignoring video-only settings. Image mode applies ZIP and file-delivery preferences. Subtitle mode applies only `subs_lang` and `subs_auto`. An explicit `/subs` works even when the embedding preference `subs_enabled` is false. Subtitle preferences do not affect other media modes. Keyboard and raw `args_json` settings are not forwarded to the worker. Cookie/proxy authorization remains separate and is still checked.

Explicit flags are mode-specific:

| Flag | Values | Modes |
| --- | --- | --- |
| `--height` | `best` or integer 1–100000 | Video, playlist, cut |
| `--video-codec` | `h264`, `h265`, `av1`, `vp9`, `any` | Video, playlist, cut |
| `--audio-codec` | `best`, `aac`, `mp3`, `opus` | Video, audio, playlist, cut |
| `--container` | `mp4`, `mkv`, `webm` | Video, playlist, cut |
| `--send-as-file` | `true`, `false` | Video, audio, image, playlist, cut |
| `--gallery-zip` | `true`, `false` | Image only |
| `--subtitle-language` | Exact language tag, such as `en`, `ru`, `zh-Hans` | Subs only |
| `--subtitle-auto` | `true`, `false` | Subs only |

Absent flags inherit relevant saved settings. Explicit `best` and `false` override saved values rather than meaning “inherit”. Duplicate, unknown, missing-value and mode-inappropriate flags are rejected. WebM requires VP9/AV1 video and explicit Opus audio. Stored `ask` requires interactive selection, which is not yet implemented, so video admission rejects it unless `--height` supplies a concrete choice or `best`. Stored audio preferences do not change video audio encoding unless an explicit `--audio-codec` is supplied.

For example, `/video --height best --send-as-file false URL` overrides a saved height limit and document delivery. `/audio --audio-codec aac URL` overrides the saved audio codec. Settings changes after admission do not alter queued processing, cache identity or same-message replay. Changing flags or other request intent under the same message ID is a conflict, not a second operation. Replay still requires current access authorization. Execution and delivery also revalidate network credentials.

Subtitle language tags contain two or three lowercase ASCII letters and at most one two-to-eight-character alphanumeric suffix. Regexes, comma lists and wildcard selection are not accepted. Track selection keeps the legacy `en`-only rule, while other languages also request their exact `-orig` track. Manual tracks take priority, and automatic tracks are eligible only when enabled. Outputs prefer SRT, then VTT, then ASS, then SSA. Other formats are rejected rather than returned through an unrestricted `best` fallback. All files must contain valid UTF-8 timing cues. ASS/SSA require a first-line `[Script Info]` header, an `[Events]` section, a declared field layout and nonempty dialogue with valid increasing start/end times. UTF-8 BOMs, CRLF, style sections, comments, comma-containing dialogue and ordinary override tags are retained. The worker validates these files as text and never renders their tags, loads fonts or converts them. ASS/SSA documents use `text/x-ssa` with their original `.ass` or `.ssa` extension. The executor checks the header signature and bounded filename separately. At most two files are returned, each bounded by both the configured artifact limit and a 4 MiB text ceiling. The aggregate byte/item budgets still apply. Unsupported formats, absent tracks or any failed track abort before delivery. Existing non-subtitle serialized requests and cache identities remain unchanged. Older binaries cannot decode stored subtitle jobs. Keep runtime and worker revisions matched, and verify rollback compatibility separately.

## Group and topic boundary

Groups stay disabled by default. Opting in does not create users or groups, change roles, or open private commands to non-owners. Identity and group records must already exist. Bot senders, anonymous `sender_chat` messages and channel posts are ignored. `/status` remains owner-private. Unauthorized group commands are silent and create no operation.

Global bans take precedence over local grants. Group enablement and topic rules apply even to the owner. An explicit group role override wins over an auto-grant. Auto-grants can elevate the effective group role without writing the global user role. Authorization is read again before execution, delivery and progress edits. Disabling groups also blocks persisted group jobs from starting after restart.

The admission reply, individual uploads, albums and cached sends retain the source chat and topic. There is no fallback into the actor's private chat or the group's General topic. A media receipt naming another topic is unconfirmed and becomes `delivery_unknown`, with no automatic resend. `/job` and `/cancel` from another topic cannot expose or change the operation, even for its original actor. Reply-message IDs may differ on subsequent commands, but the actor, bot, chat and topic must match.

## Progress-message lifecycle

Migration v5 adds one progress notice per operation. The first confirmed admission-reply message ID wins, including command replay. Startup resumes edits of known messages only. An initial `sendMessage` whose acknowledgement is lost, or a crash before its ID is persisted, cannot be retried without risking duplicate messages. That operation remains accessible through `/job`; no replacement status message is sent automatically.

Each configured tick processes one due notice, rechecks current authorization and destination, and renders the latest operation state. Unchanged text does not issue an API request. Completed, failed, cancelled, partial and uncertain deliveries stop after an acknowledged final edit. Partial and uncertain outcomes warn against blindly resubmitting. Counts describe confirmed receipts, not proof that an unacknowledged file was never received.

Edits have a bounded deadline. Network ambiguity and unknown API failures retry the same known message. Telegram `message is not modified` counts as acknowledgement, covering a lost response followed by restart. `retry_after` is persisted, with a maximum supported delay of one day; larger delays retire the notice rather than retrying too soon. Deleted/inaccessible messages and revoked access also retire the notice without creating another message. None of these edit retries can restart media delivery. The existing no-retry rule for ambiguous media sends is unchanged.

Worker tests run only in Docker via `just test-worker`. The real command scenarios live in [command-scenarios.mjs](../../backend/scripts/media-fixture/command-scenarios.mjs) and run through `just verify-media`, not a mocked Rust submission service. They inspect uploaded video/audio/clip streams and duration, immutable request parameters, replay behavior and denied/malformed requests. The command-only playlist and gallery cases cover admission and persisted parameters. Separate [batch scenarios](../../backend/scripts/media-fixture/batch-scenarios.mjs) exercise real generic HTML playlists and gallery-dl direct images through the unchanged production worker. They verify ordered album bytes, two-message receipts, whole-album cache reuse and invalid-ID recovery, incomplete API receipts, source-batch failure before sending, and an 11-item batch whose confirmed ten-item prefix survives a rejected final send, restart and replay. No live external provider is contacted. The [preference scenarios](../../backend/scripts/media-fixture/preference-scenarios.mjs) assert actual encoded height, audio codec and native/document sending, explicit `best`/`false`, admission snapshots surviving later settings changes, replay conflicts and cache-key separation.

The [gallery scenarios](../../backend/scripts/media-fixture/gallery-scenarios.mjs) use the installed Imgbox extractor without replacing its implementation. Disposable DNS pins `imgbox.com` to a documentation address. An authenticated fixture proxy maps only that address and port to the loopback HTTPS source. A one-day fixture certificate replaces trust only in the disposable test container. Without that trust mount, extraction fails before any HTTP request or media send. The successful cases compare distinct sub-1-KiB PNGs in photo/document albums, inspect all 12 ZIP members and hashes, and verify cache reuse and invalid-ID recovery. Valid small files remain cacheable under the same upper limits as uploads. A rejected ZIP preserves nine confirmed photos across restart and replay. Missing source images and the 20-item worker bound fail without sending a partial album. `just test-media gallery` runs this subset against the built images. `just verify-media` still runs every scenario.

The [adaptive scenarios](../../backend/scripts/media-fixture/adaptive-scenarios.mjs) serve generated three-second HLS MPEG-TS and separate-stream DASH through the unchanged extractors. They verify required segment requests, output stream types/duration, audio extraction, replay and restart cache reuse. Missing middle segments, redirects to a forbidden private destination and an HLS key on a forbidden private origin fail without delivery units. yt-dlp cannot skip unavailable fragments. FFmpeg may demux already-downloaded local MPEG-TS, but its protocols remain `file,pipe` and HLS/DASH/concat demuxers remain forbidden. `just test-media adaptive` runs this subset after rebuilding the images. These are finite synthetic VOD fixtures, not live-provider, DRM or encrypted-stream success coverage.

The [subtitle scenarios](../../backend/scripts/media-fixture/subtitle-scenarios.mjs) exercise the unchanged generic extractor against local HTML track markup. Native acceptance compares SRT/VTT/ASS/SSA bytes and document albums, verifies format preference, checks saved and explicit preference snapshots, language/automatic cache separation, invalid-ID recovery and restart reuse, and confirms no video GET occurs. Missing original tracks, invalid UTF-8, malformed event structure or timing, a chunked oversized body and a redirect to a prohibited private destination fail without delivery units or a cache entry. A malformed second original track cannot cause partial delivery. `just test-media subtitles` runs the focused subset against rebuilt runtime and fixture images. Container unit tests separately cover real yt-dlp manual/automatic selection and exact language matching over synthetic metadata. These checks do not establish live YouTube subtitle compatibility.

The [settings scenarios](../../backend/scripts/media-fixture/settings-scenarios.mjs) use actual served callback data to change saved preferences through the bot. They verify strict commands, EN/RU, stale callback replay after a newer choice, owner bans, foreign actors/messages/chats, inaccessible messages, restart persistence and real document/MP3 output. Settings-only actions create no media operations. Unit/integration tests also verify first-row creation, preservation of unrelated credential fields, stale revisions and unchanged admitted jobs. `just test-media settings` runs the focused subset against rebuilt images. Fixture cleanup restores the original values and revision.

The [language scenarios](../../backend/scripts/media-fixture/language-scenarios.mjs) cover EN/RU selection through served buttons, same-choice revision advancement, replay and stale menus across restart and switching back, private-owner and ban checks, and malformed callbacks. They verify saved-language priority over disagreeing Telegram metadata for new commands, callback errors and cookie-upload guidance. A real download stays on its original progress language through a `/lang` change, and the next admission uses the new choice. Language-only actions preserve unrelated user fields, settings, grants, cookies, cache and delivery history. Cleanup restores the original language, revision and ban. `just test-media language` runs this subset after rebuilding both runtime and fixture images.

The [proxy scenarios](../../backend/scripts/media-fixture/proxy-scenarios.mjs) use served revision-bearing buttons, verify missing/malformed configuration, secret-free output, stale callbacks after restart, private-owner authorization and EN/RU, and compare real authenticated proxy and direct uploads for the same URL. Callback toggles invalidate running and queued jobs in both directions without rewriting requests or delivering invalidated output. Cleanup restores the complete original settings row and revision. `just test-media proxy` runs the focused subset against rebuilt images.

The [uncache scenarios](../../backend/scripts/media-fixture/uncache-scenarios.mjs) exercise video/audio variants, cache hits before clearing, fresh upload after clearing, untouched operations/receipts and foreign cache partitions, exact-URL isolation, invalid and banned requests, EN/RU and replay after repopulation/restart. `just test-media uncache` runs this subset against rebuilt images.

The [plain URL scenarios](../../backend/scripts/media-fixture/plain-url-scenarios.mjs) verify UTF-16-prefixed entities, actual full and clipped output, saved delivery settings, restart replay and changed-intent conflicts, localized validation, silent exclusions, bans and timestamp-dialog recovery. Extended group scenarios test both this-bot reply and inline-origin triggers, ignored ordinary/foreign-bot links and topic denials. `just test-media urls` runs both against rebuilt images.

The [cut scenarios](../../backend/scripts/media-fixture/cut-scenarios.mjs) exercise actual Bot API prompts and served buttons, restarts during input and confirmation, invalid times, duplicate input, stale buttons, edit/cancel, bans, foreign callbacks, EN/RU and real clipped output. `just test-media cut` runs this subset against rebuilt images. Storage tests cover transactional state transitions and reopen. Service tests inject the admission-before-session-completion failure boundary and require the same operation on retry.

The [progress scenarios](../../backend/scripts/media-fixture/progress-scenarios.mjs) hold a real HTTP download mid-body and observe worker percentages in actual Telegram edits. They cover unchanged-text coalescing, `429` delay, a lost terminal-edit acknowledgement followed by process restart and `message is not modified`, no duplicate media or status messages, deleted-message retirement, EN/RU and authorization revocation. The test database and Bot API are disposable fixtures.

The [group scenarios](../../backend/scripts/media-fixture/group-scenarios.mjs) verify opt-in and silent denials, group-local roles without global mutation, original reply/topic routing, cached delivery to another authorized topic, albums, scoped job/cancel commands, topic revocation during a real download, and restart/replay after a wrong-topic media receipt. Native service tests also revoke group, topic or configuration access while a job is queued and assert that no worker starts.

The immediate-command slice is verified by `just verify`, `just test-worker` and `just verify-media` in `backend`, plus the root `just verify` gate. Production deployment, live provider coverage, adaptive-streaming compatibility and cutover remain outside this slice.
